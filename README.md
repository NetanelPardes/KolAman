# KolAman - מערכת לניווט התראות
## המערכת הנל מדמה מערכת אשר מקבלת התראות מ4 גופים שונים (שבכ, מוסד,אמן,פיקוד העורף ).  המערכת הנל עוקבת אחר מערך ההתראות וברגע שמגיעה התראה חדשה היא שולחת אותה לגוף שאחראי לטפל באותה התראה 



## NotificationGate
```
הסרוויס הנ"ל מדמה מערכת שמקבלת המון התראות מכל מיני גופים שונים, ושולחת אותם למערכת שתטפל בהתראות האלה 
בשביל הפרודיוסר ששולח לקאפקא השתמשתי בבדיקה האם קיים הקובץ ready
במידה והוא קיים אז קיים גם הקובץ גייסון
אז השתמשתי בפונקציה ריפלייס להחליף את הסיומתת המרתי את הטקסט שנקרא ממנו לגייסון, ושלחתי אותו לקאפקא
```

### install for NotificationGate
```bash
dotnet add package Confluent.Kafka
dotnet add package Microsoft.Extensions.Configuration.Json
dotnet add package Microsoft.Extensions.DependencyInjection
dotnet add package Serilog.Sinks.File
dotnet add package Serilo
```

## ClassifiedConsumer
```
הסרוויס הנ"ל מדמה מערכת שמקבלת את ההתראה החדשה ובודקת תקינות, מסווגת אותה ליעד הנכון, ושולחת אותה
השתמשתי פה בקונסיומר פשוט של קאפקא
קורא את ההודדעות של קאפקא
אם הם סטרינג אני ממיר אותם לגייסון
ואז אני מכניס אותם לרדיס עם TTL של 300 שניות
הפונקציה שמכניסה לרדיס היא בודקת אם הוא קיים, אם הוא קיים היא תכניס
אם לא היא פשוט תתעלם
ובחרתי דווקא להתעלם, כיוון שזה 5 דקות

בקובץ ולידציות:
קודם כל החלטתי לבדוק האם כל השדות קיימים ולבדוק שיש לכולם ערכים
אחר כך החלטתי לבדוק האם המקור הוא מוסד שבכ אמן או פיקוד העורף
אחר כך החלטי לבדוק את העדיפות
אחר כך החלטתי לבדוק את סיווג של ההתראה
החלטתי לבדוק שהסיווג הוא warnng
והחלטתי לבדוק שהקווי אורך ורוחב הם מספרים 
בנוסף החלטתי לשלוח את ההודעות דרך הרביט ב4 תורים שונים בשביל 4 הפיקודים שיש
```

## hamal
```
בסרוויס הנ"ל אנחנו מדמים פעולה של חמ"ל מתפקד
כל התראה חדשה שנכנסת למונגו הוא רואה
החלטתי לסווג את ההחלטות לפי הרמת דחיפות שלהם
אם הפריוריטי שלו שווה LOW אז אני הופך את הסטטוס שלו ל cencl
כל סטטוס אחר אנחנו הופכים את הסטטוס שלו ל INPROGRESS
ואז שולחים אותו לפונקציה שאחראית לבצע פעולה כלשהי
במקרה שלנו עשיתי שהפעולה תחכה 5 שניות ואז תהפוך את הסטטוס שלו ל DONE
```

## שיקולים אישיים
1. redis - החלטתי לזרוק כל התראה שמגיעה וקיימת כבר ברדיס, היות והרדיס שומר על ההתראה למשך זמן מסוים, היא לא נשמרת שם לנצח, למעשה היא נשמרת שם בקוד שלי למשך 5 דקות (ואפשר גם פחות). אם זה היה נשמר למשך יותר זמן הייתי שוקל לעשות עם זה משהו אחר
2. DB - במקרה של בחירת הדאטהבייס שיכנס אליו הנתונים, החלטתי להשתמש דווקא במונגו, מהסיבה המאד פשוטה שאני לא רואה פה איזשהם קשרים שצריך לעשות בין רשימה של התראות מסוימת לרשימה אחרת, בסופו של דבר זה נטו רשימה של התראות, למרות שהיה צד להשתמה ב SQL שאז השאילתות שיעשו על הטבלה יהיו יותר פשוטות (וגם זה לא בטוח)
3. pikud - בחרתי לעשות לכל אחד מ4 הפיקודים סרוויס, והסיבה היא שבסופו של דבר המערכת הזאת לא תהיה על מחשב אחד אלא כל פיקוד ישתמש בסרוויס שלו כדי לקבל את ההתראות שלו 
4. hamal - במערכ החמ"ל התבקשנו לקבל החלטה מה אנחנו עושים עם ההתראות שהתקבלו, איזה מטפלים ואיזה לא. החלטתי לא לטפל בהתראות שהעדיפות שלהם נמוכה
5. hamal - בנוסף התבקשנו לקבל החלטה מה עושים עם ההודעות שכן מטפלים בהם ואיך מטפלים בהם. פה החלטתי שכל התראה שכן מטופלת עוברת לסטטוס INPROGRESS, ונשלחת לפונקציה שעובדת ברקע. הפונקציה מקבלת את ההתראה ומחכה 5 שניות ומעדכנת את הסטטוס ל DONE , אחרי שהססטוס נהפך היא מעדכנת את המונגו עם הסטטוס החדש והזמן שלקח לו לטפל בזה
